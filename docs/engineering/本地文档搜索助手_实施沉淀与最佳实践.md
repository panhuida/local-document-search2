## 1. 文档目的

本文档用于沉淀本项目在实现 PRD、补功能、做交互优化和修复线上问题过程中，已经验证过的工程实践、注意事项和有用信息。

## 2. 已沉淀的核心原则

### 2.1 CLI 优先，Web 只复用 Service

- 所有核心能力必须先落到 `Service` 层，再由 CLI / Web 复用。
- `routes/` 只做参数解析、调用 Service、返回页面或 JSON，不要在路由里重新写业务。
- 长期看，这条原则能显著降低“CLI 能用、Web 又实现了一套不同逻辑”的分叉风险。

当前项目的主要实现边界：

- CLI 入口：`doc-cli.py`
- Web 入口：`run.py`
- 业务核心：`src/local_document_search/services/`

### 2.2 搜索模式与管理模式分离

- 搜索页的核心任务是“输入关键词并查看结果”。
- 文档索引、错误记录、清理索引属于管理任务，不应混在搜索页主流程里。
- 管理页要保持极简和紧凑，把空间尽量留给结果和状态展示。

已验证更合理的模式是：

- 搜索页：首页和结果页保持搜索引擎式布局
- 管理页：使用统一页签导航，不使用伪装成搜索框的返回入口

### 2.3 浏览器能做什么，不能做什么，要尽早讲清楚

以下需求如果仍然是“纯浏览器 + Flask 服务端”，就不能假设一定能做好：

- 浏览器直接弹出可供服务端使用的“本机目录选择器”
- 浏览器强制把系统打开的文件夹窗口置前并抢焦点
- 浏览器完全无感地接管操作系统文件打开行为

如果未来产品目标明确包含这些能力，应考虑桌面壳层方案，例如 Tauri / Electron / 本地辅助进程，而不是继续在浏览器能力边界里硬拗。


## 3. 架构与模块实践

### 3.1 长任务必须从同步请求改成后台任务

文档索引是典型长任务，不适合直接挂在一次 HTTP 请求里跑到结束。

已验证更稳的方案：

- Web 提交索引请求后立即返回
- 后台线程执行索引
- 页面通过轮询任务状态接口刷新进度
- 支持取消任务

当前实现特点：

- 索引任务服务：`src/local_document_search/services/index_task_service.py`
- 模式：进程内后台线程 + 进程内内存状态
- 状态：`queued / running / cancelling / completed / failed / cancelled`

注意事项：

- 当前任务状态不跨进程、不跨服务重启持久化
- 如果未来需要“重启后仍可追踪历史任务”，应把任务状态持久化到数据库

### 3.2 强制重索引要真正具备“修复旧数据”的能力

实践中发现，仅仅在 UI 上提供“强制重新索引”是不够的。

更稳的实现原则是：

- 强制重索引时，不要先依赖读取旧行才能继续
- 应允许直接覆盖旧记录
- 这样才能修复旧版坏数据，例如历史上的 naive 时间字符串

### 3.3 Repository 的作用域判断不能偷懒

目录清理是高风险操作，不能只做简单字符串前缀匹配。

错误做法：

- `LIKE 'D:\\docs%'`

这会把 `D:\docs2` 也误判进来。

正确做法：

- SQL 只做粗筛
- Python 再用真实路径边界做二次确认，例如 `Path.is_relative_to()`


## 4. 数据、时间与存储实践

### 4.1 全链路时间统一为 aware UTC

已经沉淀下来的规则是：

- 领域层：全部使用 aware UTC `datetime`
- 存储层：
  - SQLite：存 ISO 8601 UTC 字符串
  - PostgreSQL：后续可用 `timestamptz`
- 入口层：
  - CLI / Web 收到本地时间后，立刻转换为 aware UTC
- 展示层：
  - 页面展示时再转本机本地时间

当前关键实现：

- `src/local_document_search/utils/datetime_utils.py`

### 4.2 不要再兼容 naive 时间字符串

这次实践已经证明，被动兼容旧版 naive 时间会把问题继续往后拖。

当前更严格也更推荐的策略是：

- 数据库中如果出现 naive 时间，直接视为旧数据错误
- 优先通过重建数据库或强制重新索引修复
- 不在运行时悄悄兜底解释

### 4.3 SQLite 启动阶段不要默认全量重建全文索引

冷启动阶段应该只做轻量初始化：

- 确保表结构存在
- 确保搜索对象存在

不要每次启动都做：

- 清空 FTS
- 全量回填全文索引

这会直接破坏增量索引的价值，也会把冷启动成本放大。

### 4.4 SQLite 要显式配置并发友好参数

实际索引过程中遇到过 `database is locked`。

已经沉淀下来的做法：

- 开启 `WAL`
- 配置 `busy_timeout`

当前实现可见：

- `src/local_document_search/persistence/database.py`


## 5. 索引、转换与错误处理实践

### 5.1 默认排除 Markdown 图片目录

实践中，Markdown 笔记目录经常会带 `.assets` 图片文件夹。

如果不排除，会带来两个问题：

- 索引噪声高
- 媒体文件数量会显著拉长索引时间

当前默认规则：

- 目录名包含 `.assets` 时整棵子树跳过

可配置项：

```dotenv
EXCLUDED_DIR_KEYWORDS=.assets
```

注意：

- 显式配置为空字符串时，表示关闭默认排除规则

### 5.2 MarkItDown 超时必须可配置

真实目录验证时，大 PDF 会出现长时间卡住的问题。

已沉淀规则：

- 单文件转换超时必须可配置
- 超时要判定为 `failed`
- 超时文件要进入错误记录，便于后续重试

当前配置项：

```dotenv
MARKITDOWN_TIMEOUT_SECONDS=90
```

### 5.3 “超时失败”和“正文提取失败”要区别处理

这两类问题不应该混成一个策略。

推荐规则：

- 超时：记为失败，进入错误记录，便于重试
- 非超时的正文提取异常：允许回退成“元数据索引”

这样做的好处是：

- 长时间卡住的文件不会被误报成“已成功”
- 轻度提取失败的文档仍然可以被检索到

### 5.4 旧版二进制 Office 文件要采用分级转换策略

对 `.doc` / `.ppt` / `.xls` 这类旧版二进制 Office 文件，稳定正文提取仍然是高风险链路，但当前已经验证出一条更可用的实践：

- 优先使用 Windows 本机 Office / COM 自动化把旧格式转换为现代格式
- 转换成功后，再复用现有正文提取链路
- 如果本机没有可用 Office、`pywin32` 不可用，或 COM 转换失败，再回退为元数据索引

这样做的好处是：

- 有可用环境时，旧 Office 文件可以获得正文检索能力
- 环境不满足时，也不会把整次索引直接打崩
- Service 和 CLI / Web 的行为边界更清晰，便于排障


## 6. 搜索与预览实践

### 6.1 搜索结果页要接近用户熟悉的搜索引擎心智

这次 Web UI 优化后，已经验证比较有效的方向是：

- 首页默认就是搜索页
- 结果页保持搜索框固定在顶部
- 搜索页和结果页尽量采用用户熟悉的搜索引擎布局
- 管理入口放到次级导航，不打断主搜索路径

### 6.2 管理页不要再用“伪搜索框”

此前管理页顶部曾经出现“看起来像搜索框，实际是返回搜索”的控件。

这是错误控件隐喻，会误导用户。

已沉淀规则：

- 导航就是导航
- 搜索框就是搜索框
- 不要混用

### 6.3 预览页要以内容为中心

文档预览页的主要任务不是导航，而是阅读。

已验证更好的预览页策略：

- 去掉过重的顶部区域
- 文件信息和操作按钮放一行
- 预览内容占据主视区
- 不展示与阅读无关的状态文案

### 6.4 Markdown 渲染优先使用 `markdown-it-py`

当前已从 `python-markdown` 切换到 `markdown-it-py`。

切换后的收益：

- 表格输出更稳定
- CommonMark 兼容性更好
- 后续扩展 GFM 风格能力更自然

当前实现：

- 渲染器：`src/local_document_search/utils/markdown_renderer.py`
- 预览服务：`src/local_document_search/services/document_service.py`

### 6.5 Markdown 预览默认禁用原生 HTML

当前渲染策略是：

- Markdown 原生 HTML 不直接注入页面
- 统一转义显示

这样做的主要原因：

- 避免本地 Markdown 内容中的任意 HTML 直接进入预览页
- 简化安全边界

这意味着：

- 如果历史文档依赖内嵌 HTML 达成复杂排版，当前会看到转义后的文本
- 如果后续确实要支持更强 HTML 能力，需要再设计明确的白名单策略

### 6.6 表格“是否渲染出来”不只取决于解析器

一个重要经验是：

- 表格渲染问题，很多时候不是 Markdown 没解析
- 而是 CSS 没有给 `table / th / td` 写样式

因此，预览页的“渲染能力”必须和“预览样式”一起设计。


## 7. 文件打开与 Windows 行为实践

### 7.1 系统打开动作应走异步触发

如果直接把“打开文件”做成页面跳转，常见问题是：

- 当前页面刷新
- 标签页抖动
- 用户感知很差

当前更稳的做法：

- 页面内通过异步请求触发系统打开
- 保持当前页面不刷新

### 7.2 预览页可以新标签打开，系统打开不应强制页面跳转

已验证更符合直觉的行为：

- “预览”：新标签打开
- “打开文件” / “打开所在目录”：触发系统行为，不改变当前页面

### 7.3 Windows 下“打开所在目录”应优先使用 Explorer 定位文件

比起单纯打开目录，更推荐：

- `explorer.exe /select, 文件路径`

这样通常更容易：

- 打开正确目录
- 在资源管理器中定位具体文件

注意：

- 浏览器或 Python 进程不能 100% 保证资源管理器窗口抢到前台焦点
- 这属于操作系统窗口管理边界，不是业务代码能完全控制的事情


## 8. 页面与交互设计实践

### 8.1 减少重复导航

已验证应避免：

- 顶部一个全局导航
- 底部再放一套相同的导航

这会带来信息层级混乱。

更好的方案是：

- 搜索页保留最少导航
- 管理页用统一页签
- 页脚只保留说明性内容，或直接移除

### 8.2 管理页排版要紧凑

文档索引、错误记录、清理索引页的设计原则应是：

- 少说明、多结果
- 少装饰、多表格空间
- 少重复标题、多操作密度

### 8.3 按钮体系要统一

已经踩过的坑：

- 同一类按钮在不同页面用了不同背景类
- 某些按钮默认态不可见，鼠标移上去才显色

沉淀下来的做法：

- 把按钮抽成统一样式体系
- 把状态色也抽成统一 badge / stat-card 体系
- 后续页面只使用共享类，不再各写一套


## 9. 测试与验证实践

### 9.1 每次改动都要闭环验证

提交前必须跑：

```powershell
uv run ruff format .
uv run ruff check .
uv run pyright
uv run pytest
```

### 9.2 真实目录 smoke test 很重要

只跑 `fixtures` 远远不够。

这次多个实际问题，都是在真实目录下才暴露出来的，例如：

- SQLite 锁冲突
- MarkItDown 大文件超时
- Windows 打开目录行为异常
- 历史数据库中的旧时间格式

建议每次涉及索引链路的改动，都补一轮真实目录 smoke test。

### 9.3 页面改动建议配截图验证

适合当前项目的两种方案：

- 快速截图：浏览器原生无头截图
- 稳定交互验证：Playwright

如果页面会持续调整，推荐把 Playwright 作为长期方案。

具体命令和截图操作流程见：`docs/engineering/本地文档搜索助手_运维与排障手册.md`

### 9.4 每修一个 bug，都应补回归测试

这次实践里已经证明非常有效：

- 修数据库初始化，补测试
- 修强制重索引覆盖旧时间，补测试
- 修预览渲染和布局，补测试
- 修后台任务切页后状态丢失，补测试

规则很简单：

- 任何真实出现过的问题，只要修了，就尽量留下回归测试


## 10. 当前已知边界与后续建议

### 10.1 当前已知边界

- 索引任务状态仍然是进程内内存态，服务重启后不会保留
- 浏览器架构下无法提供真正的服务端可用目录选择器
- 浏览器无法强制操作系统窗口抢前台焦点
- SQLite FTS5 适合本地 v1，但如果中文检索体验成为核心卖点，后续应重新评估搜索后端

### 10.2 后续迭代建议

- 如果要保留索引任务历史，应把任务状态持久化到数据库
- 如果要增强 Markdown 预览，可在 `markdown-it-py` 上继续补插件能力，例如任务列表、脚注等
- 如果要做更强中文检索，应评估更适合中文全文检索的本地搜索方案
- 如果要提供真正的目录浏览和更强系统集成，应评估桌面壳层方案


## 11. 新需求落地时的简版检查清单

### 11.1 架构检查

- 是否先落到了 Service，再接 CLI / Web
- 是否复用了已有 Repository / Converter / SearchBackend
- 是否避免在路由层写业务逻辑

### 11.2 数据检查

- 是否继续遵守 aware UTC 规则
- 是否避免引入 naive 时间
- 是否会影响增量索引、强制重索引或清理边界

### 11.3 交互检查

- 是否符合搜索模式 / 管理模式分离
- 是否有重复导航
- 是否把主要空间留给结果和内容

### 11.4 验证检查

- 是否补了对应的单元 / 集成 / 回归测试
- 是否跑过四项检查命令
- 是否至少做过一次真实目录 smoke test
